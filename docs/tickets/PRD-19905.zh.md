## 需求理解

一句话：Agent Platform 要把 Rewst 的 Hyper-V 复制健康检查工作流迁移成平台原生 agent，但平台缺三样东西：(1) 临时 HTTP webhook/回调能力（脚本在远程 Windows 主机上跑完要把 JSON 结果传回来）、(2) NinjaOne 自动化脚本的穷尽发现（现有工具会把结果截断，目标脚本 `Rewst (Windows)` 没在返回里出现过）、(3) NinjaOne 组织级变量/自定义字段读取（要读 `ninja_run_as_user` 来决定脚本用哪个身份跑）。

完整的需求背景、现状调查、产品设计（目标/非目标、AC1-AC10、范围切分、Open Questions）由设计棒产出，全文见 `https://github.com/MSPbotsAI/mcp-service-gateway/blob/dev01.mbagent/PRD-19905/docs/tickets/PRD-19905.md`（mcp-service-gateway@release 5719ab2，dev01.mbagent/PRD-19905@b2c3447，2026-10-07）——那是完整十条 AC 设计的唯一事实来源，本文不逐字重复。**本文只覆盖 `Code Project` 字段改正指向这个仓库之后落在这里的那一段**（见下「本仓范围」），并追加本棒的自测/交接两节。

## 产品设计

整单的目标/非目标与十条 AC 全文见上面引用的 mcp-service-gateway 设计文档。本仓这一段交付的三个目标复述如下：

- `ninjaone_get_automation_scripts` 新增可选 `name_filter`（大小写不敏感子串）与 `limit`/`after`，使调用方无论脚本总数多少都能按名字找到目标脚本，不再受响应体积上限截断。不传参数 ⇒ 行为不变（向后兼容）。
- `ninjaone_get_device_scripting_options` 同样新增 `name_filter`。
- 新增一个只读工具，把组织级自定义字段/变量以名值对形式暴露，使 `ninja_run_as_user`（及任何其它已配置项）可读；未配置任何字段的组织会收到显式的"未配置"标注，而不是静默的空响应。

### 验收标准（本仓这一段）

- **AC1**：Given 自动化脚本总数超过 `dump_json_capped` 的 20000 字符截断阈值（如 489 个），When 调用 `ninjaone_get_automation_scripts(name_filter="Rewst (Windows)")`，Then 返回结果包含该脚本的 id/name/language 字段，不受截断影响。
- **AC2**：Given 同样场景，When 不传 `name_filter` 调用 `ninjaone_get_automation_scripts()`，Then 返回结果与改动前完全一致（含可能的截断标记）——向后兼容。
- **AC3**：Given 一台设备上可跑的脚本/动作数量很大，When 调用 `ninjaone_get_device_scripting_options(device_id, name_filter="Rewst")`，Then 返回结果只包含名称匹配的条目。
- **AC4**：Given 一个组织配置了 `ninja_run_as_user`，When 调用新的组织自定义字段工具，Then 返回结果里能读到该字段名与值。
- **AC5**：Given 一个组织什么都没配置，When 调用同一工具，Then 返回结果明确标注该字段不存在——不是报错，也不是静默省略——调用方可据此回退到 `system`。

AC6-AC10（Gap1，临时回调服务）不在本文档范围内，见上「本仓范围」。

### 从设计里带过来、本文不解决、也不阻塞本段交付的 Open Questions

- Gap2 上游 `GET /api/v2/automation/scripts` 是否支持 `pageSize`/`after` 未对真实租户核实过——本实现只在调用方传了 `limit`/`after` 时才发送这两个参数（裸调用绝不发送，保证 AC2），且无论服务端怎么处理分页，`name_filter` 始终在客户端兜底过滤。
- Gap3 的确切上游端点路径未核实——按设计文档的暂定值 `/api/v2/organization/{id}/custom-fields` 实现；若真实路径不同，只需要改这一个工具（见下「自测」→「已知缺口」）。
- `ninjaone_get_device_scripting_options` 的确切响应结构（哪个顶层 key 装脚本、哪个装动作）在本仓任何地方都没有确证——见「技术设计」→「方案选型」里过滤器为什么不猜具体 key 名。

## 技术设计

### 结论

两处改动都是给已有只读工具做增量的参数/工具面扩展，落在 `automation.py`/`organizations.py`，不碰鉴权、部署或既有签名。风险低：新参数全部可选，且无参数路径已断言与改动前逐字节一致（AC2，由 `test_no_filter_preserves_existing_truncation_behavior` 强制）。

### 现有实现定位

见上「现状」—— `automation.py:41-68`、`organizations.py`（改动前，5 个工具）、`_json.py:18-61`（`dump_json_capped`，未改）、`server.py:160-167`（工具注册——`organizations.register` 的签名未变，所以新工具不需要改这里）、`tests/test_tools.py:14-63`（清单快照，已更新）。

### 方案选型

- **Gap2/Gap3 的形状**：未考虑备选——设计文档已经定了"无备选"（标准增量修法，照 `organizations.py`/`devices.py` 现有的 `limit`/`after` 范式），本棒只需要执行。
- **`ninjaone_get_device_scripting_options` 未核实的响应结构**（本棒新做的决策，设计文档未规定）：与其去猜哪个顶层 key 装脚本列表、哪个装动作列表，冒着对真实租户过滤错字段（或完全不过滤）的风险，不如让过滤器（`automation.py` 里的 `_filter_named_lists`）遍历响应体里每一个"条目都带 name 键的顶层列表字段"并逐个过滤。这对工具自己文档承诺的"scripts"和"actions"两组在真实 API 可能采用的任何合理 key 命名下都是正确的，不需要硬编码一个未经核实的字段名。代价：如果 NinjaOne 在该响应里还返回某个本仓完全不知道、也未在任何地方见过文档的带 name 的列表字段，它也会被一起过滤——判断是可以接受的，因为这个工具本来就限定在"设备上能跑什么"这个语境内。
- **Gap2 的 pageSize/after**：实现为"调用方问了才发"而不是"总是尝试发、服务端自己决定理不理"——这保证了 AC2 的"无参数时逐字节一致"要求，不管真实 API 接不接受/忽略/拒绝这两个参数都成立，而这一点在没有真实租户的情况下核实不了。

### 数据与接口契约

```
# 改动前
ninjaone_get_automation_scripts() -> '{"scripts":[...489条...],"truncated":true,"original_count":489}'

# 改动后，无参数 —— 逐字节一致（AC2）
ninjaone_get_automation_scripts() -> '{"scripts":[...489条...],"truncated":true,"original_count":489}'

# 改动后，过滤
ninjaone_get_automation_scripts(name_filter="Rewst (Windows)")
  -> '{"scripts":[{"id":1234,"name":"Rewst (Windows)","language":"POWERSHELL",...}]}'
```

```
ninjaone_get_organization_custom_fields(organization_id=5)
  -> '{"fields":{"ninja_run_as_user":"CONTOSO\\svc-rewst"}}'                       # 已配置
  -> '{"fields":{},"note":"no custom fields configured for this organization"}'   # 未配置任何字段
```

错误处理未变——两个工具都仍走既有 `NinjaOneError` → `to_envelope()` 机制，不新增错误类型。

### 关键流程时序

与既有工具一致，无变化——同步请求/响应，走已共享的 `NinjaOneClient`/`api_client.py` HTTP 层，无新网络拓扑，无新鉴权路径。

### 非功能

- **向后兼容**：Gap2 两个工具的新参数全部可选；设计的 AC2 要求（`test_no_filter_preserves_existing_truncation_behavior` 断言）无参数调用逐字节一致，包括确切的上游请求（`client.get("/api/v2/automation/scripts", None)`，通过 mock 调用参数断言）。
- **性能**：过滤发生在客户端、取数之后；按工单所述规模（几百个脚本）开销可忽略。若 `pageSize`/`after` 服务端真支持，传了这两个参数的调用方会白得一个更小的响应体；不支持也不影响正确性。
- **安全**：无新鉴权路径，暴露的数据不超出既有组织级 API 作用域已允许的范围（自定义字段是读不是写）。本次改动不碰 authn/authz/部署（「现状」已确认：`server.py` 里 `organizations.register` 的注册调用形状未变）。

### 上线与回滚

按设计文档「上线与回滚」：本仓的改动通过 `mcp-service-gateway/scripts/vendor-deploy.sh update ninjaone` 部署，该脚本拉取 `ninjaone-mcp` 的 `main` 分支最新代码（`vendor/registry.yaml` 没有锁 ref/commit）——这个重新部署步骤是本单代码交付之外的人工操作，必须在本分支合入 `main` 之后执行，新工具才会真正对 agent 可调用。回滚是对 `main` 做一次 `git revert`，再跑同一个部署脚本；没有数据迁移、没有 schema、没有任何需要收尾的状态。

### 测试策略

按设计文档：单测用"mock 的 NinjaOneClient 避免打真实 NinjaOne API"，另外还注明要对接真实 NinjaOne 租户核实两处未确认的假设（分页参数支持、自定义字段端点路径）。本棒没有可用的 NinjaOne 测试凭据，所以：

- AC1-AC5 由 5 条 mock-client 单测覆盖（完整矩阵及证据见下「自测」）。

### 工作量与拆分

贴近设计自己对子任务 1 的估计（"1-2 人日……若都如预期支持，工作量贴近下限；若需要客户端兜底分页，贴近上限"）——落在下限附近：两处未核实的假设都用"始终正确的客户端兜底"处理掉了，不需要先摸清真实 API 行为再适配。

### 风险与依赖

- **从设计带过来、本棒未改变的依赖**：Gap2/Gap3 的代码只有在本分支合入之后有人跑了 `vendor-deploy.sh update ninjaone` 才会真正生效——这是本单交付之外的运维动作，下面「交接」再提一遍。
- **本棒实现选择带来的新风险**：如果 NinjaOne 真实的 `/scripting/options` 响应里还有第二个"脚本类"列表、但它的条目字段不是 `name`（比如叫 `scriptName`），`_filter_named_lists` 会静默跳过它、不过滤——这比猜一个具体 key 名然后过滤错字段要安全得多，但不是对真实结构正确性的保证——已在 README「Known Gaps」里标出，留给下一个有真实 NinjaOne 访问权限的人核实。
