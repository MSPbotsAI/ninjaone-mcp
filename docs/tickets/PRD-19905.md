## Requirement understanding

One line: Agent Platform needs to migrate the Rewst "Hyper-V Replication Health Check" workflow into a native platform agent, but the platform is missing three things: (1) a temporary HTTP webhook/callback capability for a script running on a remote Windows host to post its JSON result back, (2) exhaustive NinjaOne automation-script discovery (the current tool truncates results and the target script `Rewst (Windows)` never appears in the response), and (3) NinjaOne organization-level custom field/variable reads (to read `ninja_run_as_user`, which decides which identity a script runs as).

## Product design

Full goals/non-goals and the ten-AC acceptance criteria for the whole ticket are in the mcp-service-gateway design doc cited above. Restated here, the three goals this repo's slice delivers:

- `ninjaone_get_automation_scripts` gains an optional `name_filter` (case-insensitive substring) plus `limit`/`after`, so a caller can find one script by name regardless of total script count, without being cut off by the response-size cap. No args ⇒ unchanged behavior (back-compat).
- `ninjaone_get_device_scripting_options` gains the same `name_filter`.
- A new read-only tool exposes organization-level custom fields/variables as name/value pairs, so `ninja_run_as_user` (and anything else configured) becomes readable; an org with nothing configured gets an explicit "none configured" marker rather than a silent empty response.

### Acceptance criteria (this repo's slice)

- **AC1**: Given an automation-script count past `dump_json_capped`'s 20,000-char truncation threshold (e.g. 489), When `ninjaone_get_automation_scripts(name_filter="Rewst (Windows)")` is called, Then the result contains that script's id/name/language fields, unaffected by truncation.
- **AC2**: Given the same scenario, When `ninjaone_get_automation_scripts()` is called with no `name_filter`, Then the result is byte-identical to pre-change behavior (including possible truncation markers) — back-compat.
- **AC3**: Given a device with many runnable scripts/actions, When `ninjaone_get_device_scripting_options(device_id, name_filter="Rewst")` is called, Then only name-matching entries are returned.
- **AC4**: Given an organization with `ninja_run_as_user` configured, When the new org-custom-fields tool is called, Then the field's name and value are readable in the result.
- **AC5**: Given an organization with nothing configured, When the same tool is called, Then the result explicitly marks the field as absent — not an error, not a silent omission — so the caller can fall back to `system`.

AC6–AC10 (Gap1, temporary callback service) are not in this document's scope; see "Scope of this repo" above.

### Open questions carried over from the design (not resolved here, not blocking this slice)

- Gap2's upstream `pageSize`/`after` support on `GET /api/v2/automation/scripts` is unverified against a live tenant — this implementation sends them only when the caller supplies `limit`/`after` (never on the bare call, preserving AC2), and always applies `name_filter` client-side regardless of what the server did with paging.
- Gap3's exact upstream endpoint path is unverified — implemented against the design's tentative `/api/v2/organization/{id}/custom-fields`; if the real path differs, only this one tool needs to change (see Self-test, "Known gaps" below).
- `ninjaone_get_device_scripting_options`'s exact response shape (which top-level keys hold scripts vs. actions) is not pinned down anywhere in this repo — see Tech design → Option analysis for how the filter was made shape-agnostic instead of guessing a key name.

## Tech design

### Conclusion

Both changes are additive parameter/tool-surface extensions to already-read-only tools in `automation.py`/`organizations.py` — no auth, deployment, or existing-signature changes. Risk is low: new params are optional and the no-args path is asserted byte-identical to before (AC2, enforced by `test_no_filter_preserves_existing_truncation_behavior`).

### Where the current implementation lives

See "Current state" above — `automation.py:41-68`, `organizations.py` (pre-change, 5 tools), `_json.py:18-61` (`dump_json_capped`, unchanged), `server.py:160-167` (tool registration — `organizations.register`'s signature is unchanged, so the new tool needed no change there), `tests/test_tools.py:14-63` (manifest snapshot, updated).

### Option analysis

- **Gap2/Gap3 shape**: no alternative considered — the design doc already settled this as "no备选" (standard incremental fix matching the existing `limit`/`after` pattern in `organizations.py`/`devices.py`); this leg only needed to execute it.
- **`ninjaone_get_device_scripting_options`'s unverified response shape** (new decision made in this leg, not in the design doc): rather than guess which top-level key holds the script list vs. the action list and risk silently filtering the wrong one (or nothing) against a live tenant, the filter (`_filter_named_lists` in `automation.py`) walks every top-level list-of-dicts field whose items carry a `name` key and filters each one. This is correct for "scripts" and "actions" (the two groups the tool's own docstring already promises) under any reasonable key-naming the live API turns out to use, without hard-coding an unverified name. Trade-off: if NinjaOne returns some unrelated named-list field in that response (not known to exist, not documented anywhere in this repo), it would also get filtered — judged acceptable because the tool is already scoped to "what's runnable on a device."
- **Gap2 pageSize/after**: implemented as "send only if the caller asked" rather than "always send, best-effort" — this guarantees AC2's byte-identical-with-no-args requirement regardless of whether the live API accepts/ignores/rejects the params, which could not be verified without a live tenant.

### Data & API contract

```
# Before
ninjaone_get_automation_scripts() -> '{"scripts":[...489 items...],"truncated":true,"original_count":489}'

# After, no args — byte-identical (AC2)
ninjaone_get_automation_scripts() -> '{"scripts":[...489 items...],"truncated":true,"original_count":489}'

# After, filtered
ninjaone_get_automation_scripts(name_filter="Rewst (Windows)")
  -> '{"scripts":[{"id":1234,"name":"Rewst (Windows)","language":"POWERSHELL",...}]}'
```

```
ninjaone_get_organization_custom_fields(organization_id=5)
  -> '{"fields":{"ninja_run_as_user":"CONTOSO\\svc-rewst"}}'                       # configured
  -> '{"fields":{},"note":"no custom fields configured for this organization"}'   # nothing configured
```

Error handling is unchanged — both tools still route `NinjaOneError` through the existing `to_envelope()` mechanism; no new error type.

### Key flow / sequence

Unchanged from existing tools — synchronous request/response through the already-shared `NinjaOneClient`/`api_client.py` HTTP layer; no new network topology, no new credential path.

### Non-functional

- **Back-compat**: both Gap2 tools' new params are optional; the design's AC2 requires (and `test_no_filter_preserves_existing_truncation_behavior` asserts) the no-args call stays byte-identical, including the exact upstream request (`client.get("/api/v2/automation/scripts", None)`, asserted via mock call args).
- **Performance**: filtering happens client-side after the fetch; for the ticket's stated scale (hundreds of scripts) this is negligible. If `pageSize`/`after` turn out to be supported server-side, a caller that supplies them gets a smaller payload for free; if not, correctness doesn't depend on it.
- **Security**: no new credential path, no new data exposed beyond what the existing org-level API scope already permits (custom fields are read, not written). No code here touches authn/authz/deployment (confirmed by `current-state`: `server.py`'s registration call shape for `organizations.register` is unchanged).

### Rollout & rollback

Per the design's "上线与回滚": this repo's changes deploy via `mcp-service-gateway/scripts/vendor-deploy.sh update ninjaone`, which pulls `ninjaone-mcp`'s `main` branch (no `ref`/commit pin in `vendor/registry.yaml`) — that redeploy step is a manual operation outside this ticket's code delivery, and needs to happen after this branch merges to `main` for the new tools to actually become callable by an agent. Rollback is a plain `git revert` on `main` followed by the same redeploy step; no data migration, no schema, nothing stateful to unwind.

### Test strategy

Per the design doc: "用 mock 的 NinjaOneClient 避免打真实 NinjaOne API" for unit coverage, plus a note that integration against a real NinjaOne tenant is needed to confirm the two unverified assumptions (pagination param support, custom-fields endpoint path). This leg had no NinjaOne test credentials available, so:

- AC1–AC5 are covered by 5 mocked-client unit tests (see Self-test below for the full matrix with evidence).
- The two unverified-against-live-API assumptions are called out explicitly (README "Known Gaps", code comments at both call sites, and the Self-test section's "Known gaps" bullet) rather than asserted as fact — this is a recorded local blind spot, not a silent gap.
- The design's "必须手工验证" end-to-end scenario (NinjaOne script discovery → org custom field read → Gap1 round trip) cannot be run at all without Gap1 existing and a live tenant — out of this slice's scope by definition.

### Effort & breakdown

Matches the design's own estimate for sub-task 1 ("1-2 人日... 若都如预期支持，工作量贴近下限；若需要客户端兜底分页，贴近上限") — landed near the lower end: both unverified items were handled by always-correct client-side fallbacks rather than needing to discover and adapt to the live API's actual behavior.

### Risks & dependencies

- **Dependency carried over from design, unchanged by this leg**: the Gap2/Gap3 code only takes effect once someone runs `vendor-deploy.sh update ninjaone` after this branch merges — that's an ops action outside this ticket's delivery, called out again in Handoff below.
- **New risk from this leg's implementation choice**: if NinjaOne's real `/scripting/options` response shape has a *second* script-like list under a key that doesn't carry per-item `name` fields (e.g. it uses `scriptName` instead), `_filter_named_lists` would silently skip filtering it — it only filters lists whose items all carry a `name` key. This is strictly safer than guessing a specific key name and filtering the wrong field, but is not a guarantee of correctness against the live shape — flagged in README "Known Gaps" for whoever next has live NinjaOne access to confirm.
